# Weeklylog 设计

## 产品目标

Weeklylog 的核心目标是自动形成可信的工作总结，降低填写周报的成本。周度和年度视觉回顾提供额外的情绪价值，但只消费已确认事实，不承担记录或推断工作事实的职责。

## 信息流

```text
Codex / 其他 AI / Git / 手动补录
                │
             采集事件
                │
          结构化证据与摘要
                │
          保守的任务聚合
                │
             候选记录
                │
     批量确认 / 合并 / 拆分 / 忽略
                │
             正式记录
          ┌─────┴─────┐
       周报数据集    本地 outbox
          │              │
     可替换周报模板    Jira adapter（未来）
          │
       周报与视觉回顾
```

## 工作事项

一个工作事项围绕同一目标展开，并以一个能够独立写进周报的结果或明确的受阻状态收束。它可以跨越多个 AI 回合、会话、commit 和自然日；这些活动只是证据，不是独立事项。

任务边界按以下顺序判断：

1. 相同的显式 `work_item_id` 或 `task_key` 直接聚合。
2. 相同项目、相同标准化目标且时间连续的证据可以聚合为候选。
3. Jira key 是强关联线索，但不是工作事项的身份。
4. 一个 Jira issue 可以关联多个可独立汇报的工作事项。
5. 不确定时宁可分开，留给候选整理处理。
6. 正式记录绝不由后台自动合并。

## 采集与摘要

Codex 和其他 AI 客户端通过统一的 JSON 协议发送采集事件。客户端能够使用模型能力时，应发送短小的结构化字段，例如目标、摘要、结果、状态、项目和时间；weeklylog 核心不调用或绑定任何模型 API。

客户端无法生成语义摘要时，weeklylog 可以用确定性规则生成低置信度候选，但不得自动将其升级为正式记录。Git commit 可以作为辅助证据；会议、线下沟通和纯手动工作通过自然语言快速补录或未来 Jira 集成补齐。

系统必须显示采集覆盖范围，不能把 AI 可见活动描述成用户的全部工作。

## 候选与正式记录

hook、Git 和其他自动来源始终先进入候选区。用户主动添加或明确要求“记录这项工作”时，可以直接创建正式记录。

候选默认在生成周报前批量整理，支持确认、合并、拆分和忽略，也允许用户随时主动处理。周报和正式统计默认只使用正式记录；未处理候选只能进入明确标记的草稿周报。

## 时间语义

- **AI 可观测时长**：AI 客户端生命周期事件能够直接观察到的协作时长。
- **人工确认时长**：用户明确提供或确认的实际投入。
- **自然跨度**：一项工作从最早证据到最晚证据之间的日历时间，可能包含暂停和非工作时间。

三种时间不得相互冒充。缺失的人工投入不能从 AI 会话时长或自然跨度推算。

## 周报

聚合层先输出稳定的周报数据集，再由可替换模板生成 Markdown 或公司需要的格式。默认结构为：

1. 本周核心成果
2. 关键事项进展
3. 问题、阻塞与风险
4. 投入概览
5. 待确认记录
6. 用户明确记录的下周计划

AI 不得虚构成果、影响、投入时间或下周计划。

## 视觉回顾

`weekglow` 从正式记录生成每周多卡片视觉故事，`yearglow` 生成年度多页或长篇视觉回顾。两者以少字、多图和准确事实为原则，不修改 SQLite 中的工作事实，也不作为绩效看板。

## 外部集成

当前版本只完成客户端到本地 SQLite 的采集，并在工作事项变化时把稳定的集成事件写入本地 outbox，不执行网络发送。事件包含稳定的事件 ID、工作事项 ID、状态、摘要、项目、时间、分离的耗时字段和安全的证据引用。

未来 Jira adapter 默认只消费正式记录事件；支持候选审核工作流的消费者可以显式订阅候选事件。outbox 需要记录投递状态、幂等键和重试信息，避免重复创建 Jira issue。

## 隐私与保留

- 新版自动采集不落盘完整 prompt、模型回复、终端输出、diff、文件正文或密钥。
- 只保存短结构化摘要、项目、时间、客户端标识和安全证据引用；旧客户端字段仅做有界兼容裁剪。
- 为兼容旧版 SQLite 结构，自动化状态表可以保留历史字段名，但字段内容必须为空；迁移备份同样先清理这些兼容字段。候选和正式记录属于用户可审核/确认的工作事实，迁移时保留原文，避免静默数据丢失。
- 正式记录和每周复盘长期保留，用于年度总结。
- 结构化证据元数据默认保留 90 天。
- 未处理候选保留到用户处理为止。
- 已忽略候选保留 30 天后可以清理。
- 第一版保持单机、本地 SQLite，不实现多设备同步。
- 计划提供 SQLite 备份以及 JSON round-trip 导入导出能力。

## 第一版实现边界

第一版需要完成：

- 统一采集事件协议及幂等写入
- 工作事项、证据、候选和正式记录的数据模型
- 保守的候选聚合
- 候选批量确认、合并、拆分和忽略
- 分离的三种时间语义
- 稳定周报数据集和可替换模板
- 本地 outbox
- 隐私裁剪、保留和清理策略
- 数据集 JSON 导出（供周报与视觉回顾消费）

第一版不包含：

- Jira 网络 adapter
- embedding 或 weeklylog 自带模型调用
- 多设备同步
- 对会议和线下工作的完全自动发现
- 将视觉回顾作为事实来源或绩效评价工具

完整 SQLite 备份和 JSON round-trip 导入导出仍属于后续迭代；当前迁移备份只服务于 schema 升级前的安全回滚。

## 与当前实现的差距

当前实现会按每次 `Stop` 生成候选；自动化会话表中的 prompt/reply 兼容字段保持为空，旧客户端的回复字段只在内存中做有界裁剪后作为候选摘要。它尚未实现跨回合工作事项聚合、本地 outbox、候选批量合并与拆分以及完整的备份/JSON round-trip。后续实现应优先补齐这些基础边界，再扩展 Jira 或视觉能力。
